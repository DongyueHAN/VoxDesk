## 1. 这份规范要解决什么

工程文档最常见的死法有三个：**说法漂移**（同一个词三份文档三个意思）、**版本失忆**（改过什么没人知道）、**图过期**（架构图画完就再没动过）。

以下规则全部为对抗这三件事而设。规则宁少宁硬，不搞"建议性规范"。

## 2. 三条硬规则

1. **单一事实源**：`docs/` 是唯一权威。聊天记录、口头结论、Obsidian 里的散碎笔记都不算数，落进 `docs/` 才算数。
2. **时间戳不可变**：每份文档头部的 `更新` 字段只在真正改动时刷新；历史时间戳一律不改写、不覆盖。历史由 git 与 `CHANGELOG.md` 双重承载。
3. **图必须可 diff**：所有图用 Mermaid 内嵌在 Markdown 里，禁止贴截图。截图不可 diff、不可评审、过期了看不出来。

## 3. 目录与职责

├── CHANGELOG.md               变更流水（唯一记录"何时改了什么"的地方）
├── docs/

│   ├── 01-scope.md            范围 / 场景 / 非目标
│   ├── 02-requirements.md     需求池（REQ-*）
│   ├── 03-architecture.md     架构（C4 + 时序 + 状态机 + 类图）
│   ├── 04-tech-stack.md       技术栈与选型理由
│   ├── 05-roadmap.md          里程碑与任务拆解
│   ├── 06-reference-landscape.md  参考产品对照
│   ├── 07-model-layer.md      模型层：选型 / 运行时 / 预算 / 可靠性
│   ├── 08-M2process.md        M2 进程：S4–S7、时延/显存预算、闸门
│   ├── 09-web-implementation.md  当前实现验收记录（VoxDesk-Web w0.6）

│   └── adr/ADR-XXXX-*.md      架构决策记录（一事一档）
├── 调研/                      研究资料（`.gitignore` 排除，不入库）

研究资料放在仓根的 `调研/`（已被 `.gitignore` 排除），**不进版本库**；
`.obsidian/` 同理——它的存在不代表"本仓是一个 vault"，vault 根在 `D:\Obsidian\Geist`。

一份文档只回答一个问题。写不下就拆文件，不要往同一份文档里塞第二主题。

## 4. 文档头（front-matter）

每份 `docs/` 文档开头必须有字段表，字段固定为五项：

| 字段 | 取值 |
| --- | --- |
| 文档 | 相对路径 |
| 版本 | `vX.Y.Z`，与文档自身内容对应 |
| 状态 | **六个主状态之一 + 可选括注**，见 §4.1 |
| 更新 | `YYYY-MM-DD HH:mm +08:00` |
| 生效范围 | 该文档约束什么 |

### 4.1 状态取值

| 主状态 | 含义 | 当前使用 |
| --- | --- | --- |
| `草案` | 内容还会大改，不据此执行 | `02`、`03`、`05`、`08` |
| `待确认` | 内容已完整，等需求方点头 | 新文档默认起点 |
| `部分确认` | 主体已确认，个别条目悬空 | `04` |
| `现行` | 描述"现在实际在跑的东西"，随代码更新 | `09` |
| `已冻结` | 不再改；要改先开新文档或新 ADR | `00` |
| `已废弃` | 停止使用，内容留在原地 | 通常移入 `archive/` |

括注只写补充说明，**不改变主状态**：`草案（待重新基线）` 仍是草案，`部分确认（选型已定；LLM 运行时待定）` 仍是部分确认。
好处是"人能读细节、脚本能判主状态"——`check-docs` 只看第一个词。

**ADR 是例外**：用三字段 `状态 / 日期 / 相关`，不带"文档 / 版本 / 更新 / 生效范围"，见 §11.0。
原因是 ADR 是**证据**不是规范，强行补齐五字段会把一页纸变成重文档。

正文一律中文；技术名词保留英文原词（如 tool calling、cron），首次出现给中文解释，避免"上下文""语境""记忆"混用。

## 5. 版本与提交

### 5.1 版本号

`vMAJOR.MINOR.PATCH`，语义如下：

| 位 | 触发条件 | 例子 |
| --- | --- | --- |
| MAJOR | 架构冻结后发生方向性调整（换部署形态、砍掉核心能力） | v1.0 → v2.0 |
| MINOR | 新增能力、新增文档、需求新增或重排 | v0.1 → v0.2 |
| PATCH | 措辞修正、补图、改错别字、补验收标准 | v0.1.0 → v0.1.1 |

**触发升级的标准**：只要改动会影响"做什么"或"怎么做"，至少 MINOR；纯表达修正才是 PATCH。

### 5.2 时间戳

- 文档正文：`2026-10-20 12:15 +08:00`（人类可读，带时区）
- 文档头部：同上格式
- commit message 末尾：`@ 2026-10-20T12:15+08:00`（ISO 8601）
- 一律 **Asia/Shanghai**，不写 UTC、不写"昨天"

### 5.3 commit 规范

```
<type>(<scope>): <中文摘要> [vX.Y.Z] @ <ISO8601>

- 变更点 1
- 变更点 2
```

`type` ∈ `docs` / `feat` / `fix` / `chore` / `adr`；`scope` ∈ `spec` / `scope` / `req` / `arch` / `stack` / `roadmap` / `ref`。

一次 commit 只做一件事。**禁止**"顺手改一下"混提交——那会让 `git log` 失去检索价值。

### 5.4 tag

只在 MINOR 及以上打 annotated tag：`git tag -a v0.2.0 -m "..."`。PATCH 级修正不打 tag，靠 commit 追溯。

## 6. 编号体系

全仓库共用一套 ID，跨文档引用只写 ID，不写"上面那张图"。

| 前缀 | 含义 | 格式 | 示例 |
| --- | --- | --- | --- |
| `REQ-F-` | 功能需求 | `REQ-F-###` | `REQ-F-020` |
| `REQ-N-` | 非功能需求 | `REQ-N-###` | `REQ-N-001` |
| `REQ-C-` | 约束 | `REQ-C-###` | `REQ-C-001` |
| `CMP-` | 组件 | `CMP-##` | `CMP-03` |
| `IF-` | 接口 | `IF-##` | `IF-04` |
| `FLOW-` | 流程 | `FLOW-##` | `FLOW-01` |
| `ADR-` | 决策 | `ADR-####` | `ADR-0002` |
| `RSK-` | 风险 | `RSK-##` | `RSK-03` |
| `CHG-` | 变更条目 | `CHG-####` | `CHG-0007` |
| `M#` | 里程碑 | `M#` | `M2` |

ID 一经分配**永不复用、永不重排**。需求废弃时状态置 `已废弃` 并保留原 ID，不删行——删了就查不到"当初为什么不要"。

## 7. 图规范

### 7.1 图类型与用途

| 用途 | 图型 | 编号前缀 |
| --- | --- | --- |
| 系统边界与外部依赖 | C4-L1 上下文图（flowchart） | `CTX-` |
| 进程/服务级拆分 | C4-L2 容器图（flowchart） | `C4-` |
| 组件内部结构 | C4-L3 组件图（flowchart） | `C3-` |
| 一次交互的时序 | sequenceDiagram | `FLOW-` |
| 状态迁移 | stateDiagram-v2 | `SM-` |
| 领域对象关系 | classDiagram | `DM-` |
| 里程碑/路线依赖 | flowchart | `RM-` |
| 技术栈分层 | flowchart | `STACK-` |

### 7.2 强制约定

- 每张图上方一行注释：`%% diagram: FLOW-01 主链路 | updated: YYYY-MM-DD`
- 节点标签用中文 + 英文技术名词，尽量带组件 ID（如 `CMP-03 认知引擎`）
- Mermaid 只允许用这几种图型，不引入 PlantUML / draw.io / Excalidraw
- 图超过 15 个节点就该拆图，不做"一张图讲完整个系统"的幻觉
- **一张图只有一个编号**。同一张图被第二份文档复用时，要么沿用原 ID 与同一个 `updated:`（镜像），
  要么只写"见 `03` §x.y `FLOW-0n`"（引用）——**不许另起编号**。图 ID 与接口 ID 共用命名空间，
  `IF-` 前缀只给接口，不得用作图 ID

### 7.3 README 不放图（原「镜像图」规则，2026-11-11 退役）

> **本规则已于 v1.0.0 退役。** 原文要求 `README.md` §2.1/§2.2 放 `03-architecture.md` §2/§3 的镜像图，
> 用"同 ID + 同日"防止两处渲染漂移。v1.0.0 文档重构时 README 的 Mermaid 全部删除、改为 §1 龙骨 + §4 文档地图，
> **规则保护的对象已不存在**；按 §13「规则随对象一起退役」，此条一并撤掉。

现行规则只有一条：**图只画在 `docs/` 里，README 只放文字、表格与链接。**

| 允许 | 不允许 |
| --- | --- |
| README 用表格列文档地图、用链接指向 `docs/` | README 内嵌 Mermaid 图 |
| README 引用 `03` 的图 ID 与章节（`FLOW-01`、§4.4） | 把图复制一份到 README |
| README §3 进度表（它是 `05` §1 的投影，见 `05` §1.1） | 在 README 维护第二份状态

## 8. 需求写法

每条需求必须能回答"怎么算做完了"：

```
| ID | 需求 | 优先级 | 验收标准 | 状态 |
| REQ-F-020 | 系统能按用户指令启动本地程序 | P0 | 说出"打开记事本"，3s 内进程启动并语音确认 | 草案 |
```

- 优先级用 **MoSCoW**：`P0 必须` / `P1 应该` / `P2 可以` / `P3 暂不做`
- 状态用（与 `02` 头部一致）：`草案` / `开发中` / `已实现` / `已验收` / `未达标` / `已废弃`；**没有证据的一律 `草案`**
- 需求写"系统能……"，不写"用户想要……"——后者无法验收
- 一条需求只描述一个可观测行为，不写"并且支持 A、B、C"

## 9. 追踪矩阵

`docs/02-requirements.md` 末尾维护一张矩阵，保证需求不悬空：

| 需求 | 落到的组件 | 相关流程 | 相关决策 |
| --- | --- | --- | --- |
| REQ-F-020 | CMP-04 工具运行时 | FLOW-01 | ADR-0002 |

新增需求必须至少填入一个组件；填不出组件时写 `无组件（原因）`，约束类（`REQ-C-*`）可留 `—`。
又填不出组件、又给不出原因的，说明需求还没想清楚，标 `草案` 挂着。

## 10. 一次标准更新的完整动作

每次对话产出内容后，按序执行：

1. 改受影响的文档正文
2. 刷新该文档头部 `版本` 与 `更新`
3. 在 `CHANGELOG.md` 顶部追加条目（版本 + 时间 + 摘要 + 关联 ID）
4. 更新追踪矩阵（如涉及需求）
5. `git add` → `git commit`（按 5.3 格式）→ 必要时 `git tag`
6. 若属方向性选择，补一份 `docs/adr/`

> 这套流程的本质：**让"这份文档为什么长这样"可被追溯**。面试被问"这个决策怎么来的"，能翻出 ADR 和 commit，比口头解释有力得多。

## 11. ADR 生命周期（决策如何被推翻）

ADR 是**决策档案**，不是法律。决策会变——尤其是"读了开源实现之后发现原判断错了"这种变。**允许改结论，但必须留下改的痕迹。**

### 11.0 ADR 的格式（三字段，不是五字段）

ADR 是决策的**快照**，不维护版本、不跟文档一起改。三个头字段：

| 字段 | 取值 |
| --- | --- |
| 状态 | `提议` / `生效` / `已取代` / `已废弃`（见 §11.1） |
| 日期 | 决策落档时间，`YYYY-MM-DD HH:mm +08:00`，**此后不再改** |
| 相关 | 关联的 `REQ-*` / `CMP-*` / `ADR-*` ID |

正文四段、顺序固定：`## 背景` → `## 决策` → `## 理由` → `## 代价`（写不出代价的决策，通常是没想清楚代价）。

现有 10 份 ADR 全部已是此格式，**不要求**补成五字段。

### 11.1 四个状态

| 状态 | 含义 | 能否被正文引用为依据 |
| --- | --- | --- |
| `提议` | 写出来了，尚未纳入当前基线 | 不能，只能当讨论稿 |
| `生效` | **当前按它执行**；`00`~`10` 引用它 | 能 |
| `已取代` | 被新 ADR 取代，原文保留 | 不能，要去看新 ADR |
| `已废弃` | 不再适用，且没有替代 | 不能 |

### 11.2 推翻一份 ADR 的固定动作

1. **新建** `docs/adr/ADR-XXXX-*.md`，标题写**新结论**；"背景"里必须写明：因为读了哪个开源实现 / 哪次实测，推翻了 `ADR-YYYY` 的**哪一条**判断；
2. **原文件只改一行**：`状态` → `已取代（by ADR-XXXX，YYYY-MM-DD）`；
3. **禁止**删除原 ADR，**禁止**改写它的"决策""理由"段落——那是历史证据；
4. 同步改受影响的正文（`00`~`10`），并在 `CHANGELOG.md` 记一条 `CHG-`；
5. 若被推翻的是**方向性**决策（例如半双工 → 全双工），按 §5.1 升 **MAJOR**。

### 11.3 什么样的"学习"足以推翻决策

| 够格 | 不够格 |
| --- | --- |
| 亲手跑了开源实现，拿到与文档相反的实测（延迟、字错率、内存占用） | 只看了 README，觉得"人家做得更好" |
| 发现选定的库已归档 / 许可变更 / 不支持 Windows | 觉得另一个框架更流行 |
| 落地时发现接口装不下（如 `archive/09-tts-module.md` §3.3 的流式边界） | 想换换口味 |

一句话：**推翻决策要付证据，不是付情绪。**

这三项从 v0.1.0 起就以"建议"的形式在跑，却一直挂着"待确认"。2026-11-11 按**实际执行情况追认**为决议：

| # | 事项 | 决议（= 三个月来的实际做法） | 落地位置 |
| --- | --- | --- | --- |
| 1 | 文档语言 | **中文正文 + 英文术语**；英文摘要另附，不写进正文 | 全仓；本文件 §4 末段 |
| 2 | 文档是否入 git | **入本仓**；研究资料放 `调研/` 并被 `.gitignore` 排除 | 本文件 §3 |
| 3 | 版本粒度 | **每次实质更新升 MINOR，里程碑打 tag；PATCH 不打 tag** | 本文件 §5.1 |

> 追认不是"补个形式"：这三条已被几十个 commit 实际执行，继续挂着"待确认"，只会让本文件永远无法冻结。

## 13. 规则的追溯范围

**本规范只约束当前文档，不追溯 `docs/archive/`。**

| 规则 | 对 `archive/` 是否适用 |
| --- | --- |
| 五字段头、状态枚举、`vX.Y.Z` | ❌ 不适用：归档件保留退役时的原样 |
| 图 ID 前缀（§7.1） | ❌ 不适用：`TTS-01` 等旧前缀保留 |
| 链接可达 | ✅ 适用：死链随时可修，不改变内容 |
| 不得改内容 / 不得改时间戳 | ✅ 强制：归档件是证据 |

**规则要随对象一起退役**：一条规则保护的对象消失时（如 §7.3 的 README 镜像图），规则本身必须标退役并写原因，
不能留在规范里当装饰——否则下一个人会照着一条已经不成立的规则干活。
