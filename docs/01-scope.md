## 1. 定位

**一句话**：给 PC 装一个能干活儿的语音嘴替——你说一句，它去开程序、调接口、排日程、跑一段自动化，然后把结果说回来。

**一句话的边界**：它是**单机、单用户、任务型**的语音 Agent，不是聊天玩具，也不是全双工对话系统。

## 2. 目标用户与使用情境

用户 = 你自己（单机、单人、Windows）。这决定了三个关键取舍：不需要多租户、不需要高可用、不需要鉴权体系。

三个典型场景（也是简历上的故事素材）：

| 场景 | 用户说 | 系统要做的事 |
| --- | --- | --- |
| **即时执行** | "帮我把记事本打开" | 意图识别 → 工具调用 → 启动进程 → 语音确认 |
| **信息获取** | "查一下明天杭州的天气" | 工具调用外部 API → 组织自然语言 → 播报 |
| **定时自动化** | "每天早上九点帮我总结一下科技新闻" | 解析 cron → 持久化任务 → 到点触发 → 多步执行 → 主动播报 |

## 3. 范围（In Scope）

| 域 | 内容 |
| --- | --- |
| 语音输入 | 按键说话（PTT）、VAD 断句、流式转写 |
| 语音输出 | TTS 播报、可中断 |
| 对话 | 多轮上下文、意图分流、槽位澄清 |
| 工具 | 本地程序启动、HTTP API 调用、文件操作、工具注册与发现 |
| 自动化 | 一次性延时任务、cron 周期任务、任务查询/取消 |
| 智能体 | 多步任务（计划→执行→观察→修正）、进度播报、中断 |
| 治理 | 工具白名单、危险操作确认、审计日志、可观测性 |

## 4. 非目标（Out of Scope）

明确写出来，避免范围蔓延，也避免面试时被"为什么不做 X"问住。

| 非目标 | 理由 |
| --- | --- |
| **全双工 / 免按键打断式对话** | 这是另一个量级的问题（AEC、端点判定、双工状态机）。当前项目要的是"任务完成度"，不是"对话自然度"。留作 M6 之后的可选延伸。 |
| **自研 ASR / TTS / LLM** | 工程价值在编排与执行，不在模型训练。全部走 API，本地只留替换点。 |
| **唤醒词常驻监听** | KWS 误唤醒率与功耗是独立工程问题，PTT 已足够验证链路。列为 P2。 |
| **多设备 / 移动端 / 云端部署** | 单机场景不需要，加了只增加复杂度，不加分。 |
| **图形界面（除托盘）** | 交互主通道是语音；托盘只做状态与设置。 |
| **多用户与权限体系** | 单用户本机，权限只需"危险操作二次确认"这一层。 |

## 5. 与参考产品的关系

| 参考对象 | 我们取什么 | 我们不取什么 |
| --- | --- | --- |
| **小爱同学** | 技能路由的形态、定时提醒的产品化方式、"一句话完成一件事"的交互预期 | 端云一体的硬件形态、唤醒词、内容生态 |

## 6. 成功标准

项目"做成了"的判定，不看代码量，看这四条能否演示：

1. 说出"打开记事本"，3 秒内程序启动并有语音反馈；
2. 说出"每天早上九点提醒我站会"，次日 9:00 主动播报，重启电脑后任务仍在；
3. 说出一个多步任务（如"帮我查下这周有哪些 AI 会议，整理成三条"），系统能自行拆解、调用工具、汇报进度；
4. 全程有审计日志，能回答"昨天下午它到底执行了什么"。

## 7. 简历定位（写给自己看）

这段是给未来的自己提醒：**面试官不关心你调了几个 API，关心你是否理解系统边界与工程取舍。**

要能讲清的三件事：

- 为什么是 PTT 而不是唤醒词（成本/收益/风险）
- 工具层为什么用注册表而不是直接写 if-else（可扩展性、可测试性）
- 定时任务为什么用 APScheduler + SQLite 而不是消息队列（单机场景的过度设计问题）
