## 1. 为什么看这两个产品

- **小爱同学**：中文语音助手的产品化标杆——"一句话完成一件事"的交互预期、技能体系、定时提醒，都是现成答案。
- **OpenClaw**：单机个人 Agent 的工程化标杆——网关、Agent 循环、工具/插件、定时任务、审批与沙箱，是一套被真实使用验证过的分层。

一个给"产品形态"，一个给"工程结构"。我们取二者的交集，砍掉与单人 PC 场景无关的部分。

## 4. 三个可直接迁移的设计模式

### 4.1 能力注册表（Registry Pattern）

小爱的"技能"、OpenClaw 的"工具/插件"，本质都是**一张能力清单 + 统一的描述格式**。模型只需要看到这张清单，就能决定调谁。

对我们意味着：新增一个能力 = 注册一条 `ToolSpec`，不改编排代码。这是 `REQ-F-023` 的来源。

### 4.2 四段式执行链

三家的链路惊人一致：

```
听清（ASR） → 想明白（意图/工具选择） → 办到（执行） → 说回来（TTS）
```

差异只在"办到"这一段的深度：小爱止步于云端技能，OpenClaw 深入到本机 shell，我们取中间——**本机程序 + 外部 API + 定时任务**。

### 4.3 任务与对话解耦

小爱的提醒、OpenClaw 的 cron，共同点是：**任务的生命周期远长于一次对话**。任务必须独立持久化，不能挂在会话对象上。

对我们意味着：`tasks` / `jobs` 独立建表，调度器与网关不共享内存状态（见架构文档第 5 节）。

## 5. 我们明确不学的部分

| 不学 | 原因 |
| --- | --- |
| 唤醒词常驻 | 误唤醒率、功耗、隐私三重成本，PTT 已够验证 |
| 多渠道接入 | 单人单机，一个入口足够；多加渠道只是增加适配工作量 |
| 多 Agent 编排 | 单任务场景用不上，且显著抬高标准 |
| 沙箱隔离 | 本机单用户，用"白名单 + 审批"性价比更高 |
| 设备生态 / 智能家居 | 需要硬件与生态，与项目目标无关 |
