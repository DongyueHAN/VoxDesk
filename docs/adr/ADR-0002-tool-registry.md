# ADR-0002 · 工具层以内置 Registry 为核心，MCP 仅作扩展

| 字段 | 值 |
| --- | --- |
| 状态 | 已提议 |
| 日期 | 2026-10-20 12:12 +08:00 |
| 相关 | REQ-F-023、REQ-F-024、REQ-F-050 |

## 背景

"打开程序""调 API""查文件"三类能力需要一个统一的暴露方式，供 LLM 发现与调用。候选：

- **A**：if-else 硬编码（最快，但不可扩展）
- **B**：内置 Tool Registry（统一 schema，进程内调用）
- **C**：直接全面采用 MCP（Model Context Protocol，每个工具一个独立进程）

## 决策

采用 **B，并为 C 预留适配器**：核心是进程内的 `ToolSpec` 注册表；MCP 作为外部工具接入协议，通过一个 `MCPToolAdapter` 把 MCP server 包装成普通 ToolSpec。

## 理由

1. 单机场景下，每个工具起一个 MCP 进程的启动开销与调试成本都不划算。
2. LLM 只需要看到 `name / description / JSON Schema` 三件套——Registry 已完全满足，与 MCP 在信息层面等价。
3. 保留 MCP 适配器有两个好处：能复用社区生态；简历上体现对协议演进的理解。

## 后果

- **正面**：新增工具只写一个类 + 注册一行；工具可单测（纯函数式 handler）。
- **负面**：进程内执行缺少隔离，一个工具的崩溃可能带走主进程。
- **缓解**：每个工具调用包超时与异常捕获；高风险工具走子进程执行。

## 风险分级

| 级别 | 例子 | 策略 |
| --- | --- | --- |
| `read` | 查天气、读文件 | 直接执行 |
| `write` | 新建文件、发消息 | 记录审计，可配置确认 |
| `danger` | 删除、关机、执行任意命令 | **必须二次确认** |
