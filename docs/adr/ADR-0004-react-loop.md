# ADR-0004 · 多步任务采用 ReAct 循环 + 硬性上限

| 字段 | 值 |
| --- | --- |
| 状态 | 生效 |
| 日期 | 2026-10-20 12:12 +08:00 |
| 相关 | REQ-F-040、REQ-F-041、REQ-F-043 |

## 背景

"帮我查三个 AI 会议并整理成三条"这类请求，单次工具调用无法完成，需要多轮"思考-行动-观察"。候选：

- **A**：预先写死工作流（每种任务一条流水线）
- **B**：ReAct 循环（LLM 自主决定下一步）
- **C**：先规划再执行（Plan-and-Execute，计划一次生成，逐步执行）

## 决策

采用 **C 的骨架 + B 的纠错**：先让模型产出步骤清单，再逐步执行；每步执行后允许模型根据观察结果修正剩余步骤。同时施加**三重上限**：步数 ≤ 8、单步超时 30s、总时长 ≤ 5min。

## 理由

1. 纯 ReAct 在中文口语任务上容易"边想边跑偏"，先规划能显著提升可解释性（也能播报"我打算分三步"）。
2. 执行中允许修正，避免计划一旦错了就全盘失败。
3. 上限是必需品：没有上限的自主循环 = 不可控的账单与不可预期的行为。

## 后果

- **正面**：复杂任务可完成；过程可播报；失败有边界。
- **负面**：多一次 LLM 调用（规划），首响变慢。
- **缓解**：简单任务跳过规划直接执行（由 Decision 分流判断）。

## 与全双工的关系

多步执行期间用户可能插话。当前设计是"执行中仍可接收中断指令（停/取消）"，但不支持边执行边对话——那属于全双工范畴，明确不在本项目内。
