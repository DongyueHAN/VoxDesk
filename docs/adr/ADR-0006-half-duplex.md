# ADR-0006 · 半双工优先，全双工列为可选

| 字段 | 值 |
| --- | --- |
| 状态 | 生效 |
| 日期 | 2026-10-26 14:30 +08:00 |
| 相关 | REQ-C-007、REQ-F-003、REQ-F-008、REQ-F-013 |

## 背景

"全双工"意味着麦克风与扬声器同时工作，用户可以在系统播报时直接插话。它需要三样东西：

1. **AEC（回声消除）**——否则系统会听到自己的声音
2. **持续 VAD**——判断插话是"打断"还是"嗯嗯"这类反馈
3. **双工状态机**——处理"播报中被截断"的语义

这三样在任何一项上翻车，体验都比半双工更差。

## 决策

**先做半双工**：同一时刻只有一条音频通道活跃。

| 状态 | 麦克风 | 扬声器 |
| --- | --- | --- |
| Listening | 开 | 关 |
| Thinking | 关 | 关 |
| Speaking | **关** | 开 |

打断通过**全局热键**实现：按下 → `flush()` 停止播报 → 立即转 Listening。

全双工列为 **P3**，架构预留 `AECStage` 与 `BargedIn` 事件（见 `03-architecture.md` §7）。

## 理由

1. **成本收益比**：AEC + 双工判定是独立的研究级问题，投入 3 周可能换来"偶尔能打断"。
2. **风险隔离**：先证明"能听懂、能干活"，再谈"能自然插话"。
3. **工程红利**：播报时关麦，直接消灭了自激与回声这两个最难调的问题。
4. **符合项目定位**：任务型助手对"插话"的敏感度，远低于闲聊型伴侣。

## 后果

- **正面**：M1/M2 可以在没有 AEC 的前提下跑通；调试面大幅缩小。
- **负面**：播报中不能语音打断，必须按热键——这在演示时会被注意到。
- **缓解**：把"热键即停"做成体验亮点（响应 < 200ms），并在文档里明确说明这是阶段性取舍。

## 为什么不"先做一个粗糙的全双工"

粗糙的全双工 = 频繁自激 + 误打断 + 说不完一句话。它会同时毁掉"听"和"说"两条链路的可信度，是最差的中间态。
