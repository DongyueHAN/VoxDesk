# ADR-0007 · 语音管线自研，LLM 用 Ollama

| 字段 | 值 |
| --- | --- |
| 状态 | 已提议 |
| 日期 | 2026-10-26 14:30 +08:00 |
| 相关 | REQ-F-060、REQ-F-064、REQ-N-001 |

## 背景

语音 Agent 有两类现成骨架可选：Pipecat、LiveKit Agents。推理侧也有多种选择：Ollama、llama.cpp server、vLLM、LM Studio。

## 决策

**语音管线自研（asyncio + Frame/Stage），LLM 推理用 Ollama。**

## 理由：为什么不用 Pipecat

| 维度 | Pipecat | 自研 |
| --- | --- | --- |
| 上手速度 | 快（半天出 demo） | 慢（3–5 天） |
| 可控性 | 中（被框架的 Frame 模型约束） | 高 |
| 调试 | 需要理解框架内部 | 完全透明 |
| 简历价值 | "用过框架" | **"设计过管线"** |
| 换 TTS/ASR | 有现成集成 | 自己写适配器（约 100 行） |

本项目的核心命题是"**如何编排端侧语音链路**"。用框架等于把最该展示的部分外包给别人。此外 Pipecat 的抽象以云服务为默认假设，本地模型的流式接口需要额外适配。

**但吸收它的两个好设计**：

1. **Frame 模型**——所有数据（音频帧、文本、控制信号）统一为 Frame，在 Stage 间传递
2. **可中断的播放句柄**——`flush()` 语义，与 ADR-0006 的按键打断直接对应

## 理由：为什么 Ollama

| 维度 | Ollama | llama.cpp server | vLLM |
| --- | --- | --- | --- |
| 安装 | 一条命令 | 需自备 GGUF + 参数 | 需 GPU 环境 |
| 模型管理 | `pull/list/rm` | 手动 | 手动 |
| 结构化输出 | `format: json` | **GBNF 语法（最强）** | 支持 |
| 性能调优 | 有限 | 细粒度 | 高吞吐 |
| 结论 | ✅ 起步 | ✅ 进阶 | ❌ 单机无收益 |

Ollama 的 OpenAI 兼容接口让"换引擎"变成改一个 `base_url`。当 JSON 合法性成为主要故障源时，再切 llama.cpp 上 GBNF。

## 后果

- **正面**：链路完全可控；每一层都可替换；面试时能逐帧讲清数据怎么流动。
- **负面**：多花 3–5 天；要自己处理背压（backpressure）与取消传播（cancellation）。
- **风险**：自研管线容易写出"队列堆积"，必须在 M1 就把 `queue.maxsize` 与丢帧策略定好。
